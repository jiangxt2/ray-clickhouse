# ray-clickhouse 1.0

## Highlights

- Adopt the two-component `major.minor` version route, starting at `1.0`.
- Read trusted SELECT/WITH query results into Ray Datasets with named value bindings, validated result aliases, schema probes, and a single data-read task.
- Select an eligible leading integer sorting key with opt-in `split="auto"` range planning for direct MergeTree-family tables.
- Bind typed scalar filter values on the ClickHouse server, including nullable values and precision-aware datetime and decimal hints.
- Attach generated query IDs and bounded client diagnostics to read failures, with best-effort server query-log lookup and optional explicit log flushing.
- Retain structured table reads, single-query View and Distributed reads, bounded Arrow streaming, and validated partition and integer-range splits.
- Retain schema-checked synchronous and confirmed asynchronous append writes, explicit restricted `create`/`overwrite` modes, and fail-closed errors.

## Compatibility

- Python `>=3.10,<3.14`.
- Final Ray releases `>=2.55,<2.59`.
- PyArrow `>=19,<20`.
- `clickhouse-connect[arrow] >=1.5,<1.6`.
- ClickHouse 26.8.1.2041 and the Ray 2.58.0/Python 3.12 three-node runtime are the pinned integration baselines.

## API and consistency boundaries

- Package-root exports remain `read_clickhouse()`, `write_clickhouse()`, `WriteReceipt`, and the documented error hierarchy.
- Query reads accept the documented trusted SELECT/WITH subset. They reject multiple statements, DDL/DML, output formats, output files, and inline settings, and enforce `readonly=1`.
- Metadata probes and data reads are independent requests. Multiple queries or read tasks do not share a database snapshot.
- Automatic range planning is opt-in; the default remains `split="single"`. Unsuitable sorting keys follow the configured discovery policy, while authentication, permission, and transport errors still raise.
- Typed binding does not accept collection or identifier hints, mixed binding styles, or unrestricted SQL execution.
- Diagnostic query-log lookup never replays a failed query. `diagnostic_flush_logs=True` requires permission to run `SYSTEM FLUSH LOGS`.
- There is no arbitrary DDL, delete, update, upsert, connector-side Distributed shard routing, cross-task transaction, snapshot-isolation, or exactly-once guarantee.
- MaterializedView reads remain outside the supported capability profile. Uncertain writes or table management require application-level reconciliation.

## Release integrity

The master-push CI produces and attests one wheel/source-distribution pair for the exact release commit. The promotion workflow reuses those files through dry-run, TestPyPI, annotated tag, PyPI, and GitHub Release stages, verifying checksums, provenance, integration evidence, and predecessor receipts.
